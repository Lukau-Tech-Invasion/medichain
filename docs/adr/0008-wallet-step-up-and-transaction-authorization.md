# ADR-0008: Wallet Step-Up and Exact Transaction Authorization

- **Status:** Proposed
- **Date:** 2026-08-25
- **Deciders:** Founder
- **Related:** [ADR-0003](0003-wallet-auth-with-jwt.md), AUTH-003, AUTH-005, APP-001, AUD-001, DATA-001

## Context

MediChain is migrating production identity provenance to verified JWT sessions.
A valid Bearer token identifies an authenticated user through the verified `sub`
claim.

The current architecture does not, however, provide a clean mechanism for
requiring additional wallet proof during an already-authenticated Bearer
session. Historically, wallet-signature verification was coupled to
`X-User-Id`. Retaining that model would recreate duplicate identity provenance
after AUTH-003 removes legacy identity headers.

MediChain therefore requires a distinction between:

1. ordinary authenticated session activity;
2. recent stronger authentication for privileged operating contexts; and
3. explicit authorization of an exact consequential transaction.

These controls must not permit downgrade to legacy identity mechanisms.

## Decision 1 — Session identity

Access tokens SHALL contain an opaque `sid` session identifier in addition to
the existing authenticated subject.

`sub` identifies the user.
`sid` identifies one authenticated login/device session.
`jti` identifies one particular JWT.

The `sid` SHALL:

* be generated by the server using cryptographically strong randomness;
* contain no patient, wallet, employee, email, or other identifying information;
* remain stable across access-token and refresh-token rotation within the same session;
* change when a new independent login session is established;
* correspond to a durable server-side session record;
* be revoked by logout of that session;
* allow logout-all to revoke every active session belonging to the subject.

The database session record, not JWT claims alone, remains authoritative for
revocation and elevated-assurance state.

## Decision 2 — Identity source

Bearer-authenticated requests SHALL derive identity only from the verified JWT
`sub`. A wallet signature SHALL NOT introduce or override identity. No
high-assurance Bearer request may require `X-User-Id`.

When wallet verification is required, the server SHALL:

1. verify the Bearer token;
2. derive `sub` and `sid`;
3. load the currently authorized wallet credential or credential set associated with that subject;
4. verify the wallet proof against that server-authorized credential.

A client-supplied identity header SHALL NOT select the wallet whose signature is
trusted.

## Decision 3 — Three assurance classes

### Class A — Ordinary authenticated operations

Bearer authentication is sufficient for normal operations that are already
permitted by role, resource relationship, organisation boundary, consent, and
other authorization rules. Examples: dashboard/navigation; scoped clinical
reads; appointments; ordinary messaging; routine vitals and triage entry; draft
clinical documentation; other reversible routine workflow mutations that do not
change authority or create an exceptional privilege.

Existing authorization, idempotency, audit, and resource-scoping requirements
still apply.

### Class B — Session step-up

A recent wallet challenge SHALL be required before entering privileged
operating contexts where stronger assurance is justified but requiring a
cryptographic signature for every subsequent action would create signing
fatigue. Initial examples: privileged administration surfaces; security
administration; broad authorized patient-search or audit-review surfaces;
privileged operational controls; other explicitly classified sensitive contexts.

Successful wallet step-up updates the durable session associated with `sid`.
The initial elevated-assurance lifetime is 10 minutes.

Step-up state SHALL NOT survive session revocation, logout, logout-all, wallet
credential revocation, or expiry of the configured step-up interval.

A successful step-up does not automatically authorize a transaction that
requires Class C exact signing.

### Class C — Exact transaction authorization

Exact transaction signing SHALL be required when an action:

* changes another actor's authority or privilege;
* changes identity/authenticator bindings;
* creates or modifies exceptional emergency authority;
* grants, approves, denies, or revokes sensitive access or consent;
* causes irreversible or externally released PHI disclosure;
* authorizes retention/destruction;
* issues or revokes an identity/NFC credential;
* or finalizes an authoritative clinical instruction or attestation on which
  another actor or system is expected to rely.

Initial Class C operations: patient access grant/revoke; consent grant/revoke
where the action changes downstream access; maker-checker approval or denial;
staff role assignment/revocation; guardian authority creation/change/revocation;
break-glass issuance, extension, and revocation; NFC/identity credential
issuance and revocation; wallet/authenticator replacement or revocation;
trusted-device authority changes; retention/destruction approval or execution;
bulk PHI export/disclosure; final signing of treatment orders and other clinical
records that become authoritative instructions or attestations.

Draft editing and routine autosave SHALL NOT require exact transaction
signatures.

Where the exact transaction signature itself requires fresh user interaction
with the wallet authenticator, that signature satisfies the wallet step-up
requirement for that transaction. MediChain SHALL NOT require two consecutive
wallet prompts for the same action merely to satisfy both Class B and Class C.

## Decision 4 — Exact signed challenge

The server SHALL generate the transaction-authorization challenge. The challenge
SHALL be short-lived, single-use, and cryptographically bound to the
authenticated session and exact intended mutation.

The canonical signed representation SHALL contain at least: protocol/version
identifier; audience/domain; authenticated `sub`; authenticated `sid`; action
identifier; HTTP method; normalized request path; digest of the canonical
request body; target resource identifier; target resource version or equivalent
concurrency token when applicable; idempotency key for mutations subject to
idempotency; cryptographically random nonce; issuance timestamp; expiration
timestamp.

The initial challenge lifetime SHALL be no more than 120 seconds.

The challenge SHALL be invalid if significant transaction information changes
after challenge creation. Approval of resource version N SHALL NOT authorize
resource version N+1.

## Decision 5 — Verification order

For a Class C request, the server SHALL verify:

1. Bearer token validity;
2. session status and revocation using `sid`;
3. authenticated subject from `sub`;
4. currently authorized wallet credential belonging to that subject;
5. challenge ownership by `sub` and `sid`;
6. challenge expiration and single-use state;
7. method and path binding;
8. canonical body digest;
9. target resource identifier/version;
10. idempotency-key binding where applicable;
11. wallet signature;
12. ordinary role/resource/relationship authorization;
13. consent and purpose restrictions where applicable;
14. any maker-checker or separation-of-duties rule;
15. the final transaction-authorization gate immediately before mutation.

Failure of stronger authentication SHALL NOT fall back to a legacy identity or
weaker authorization mechanism.

## Decision 6 — Transactional completion

For critical Class C operations, consumption of the one-time authorization
challenge SHALL be coordinated with the business mutation and required audit
event so that the system cannot successfully execute an exact signed operation
twice.

The implementation SHALL define and test failure behavior for: database
rollback; audit-outbox failure; duplicate submission; concurrent submission;
response loss; application restart.

## Decision 7 — User intent

Exact transaction authorization SHALL present enough significant information for
the user to understand what is being authorized. The UI SHALL avoid blind
signing of opaque hashes. At the same time, wallet prompts SHALL minimize
unnecessary PHI disclosure to external wallet software. The final display
contract for each Class C action SHALL identify only the minimum significant
fields necessary for informed authorization.

## Consequences

**Positive.** JWT `sub` remains the single identity authority. AUTH-003 does not
need to retain `X-User-Id` for wallet signing. Wallet possession can strengthen
an already-authenticated session. High-risk mutations receive explicit
transaction authorization. Challenges can be bound to an exact session without
binding to a particular short-lived JWT rotation. Session revocation and step-up
state remain centrally enforceable. Resource-version binding prevents
approval/signature reuse after material state changes.

**Costs.** Access-token schema changes to include `sid`. Auth-session
persistence and middleware must expose the durable session identity. Client and
server require a new wallet challenge/signing protocol for Bearer sessions.
High-risk workflows require UX for meaningful transaction confirmation. Browser
and direct-API security tests become mandatory before release.

## Required validation

The implementation is not complete until tests prove at least: valid Bearer +
valid matching wallet proof succeeds where required; Bearer for user A + wallet
proof for user B fails; Bearer for user A + attempted `X-User-Id: B` never
changes effective identity; expired Bearer never downgrades to legacy identity;
revoked `sid` rejects step-up and exact transaction authorization; wallet
credential revocation invalidates later signing; challenge replay fails; expired
challenge fails; modified path fails; modified body fails; modified resource
version fails; different `sid` fails; duplicate/concurrent execution produces
one authorized mutation; exact signing does not authorize a materially changed
transaction; ordinary Class A operations do not unnecessarily require signing;
browser tests demonstrate both successful signing and denial behavior.

## Deferred

This ADR does not convert all Bearer access tokens into DPoP or otherwise
require a signature on every API request. A future sender-constrained-token
architecture may be evaluated separately if the threat model justifies it.

## Implementation review — prerequisites and open questions (2026-08-25)

Raised while checking each decision against the current code. Recorded here
rather than silently amending the decisions above, because several are choices
for the deciders. **This ADR should not move from Proposed to Accepted until
items 1 and 4 are answered**, because both change what gets built.

### 1. Decision 1 is contradicted by the current rotation implementation — BLOCKING

Decision 1 requires `sid` to "remain stable across access-token and
refresh-token rotation within the same session." `auth_sessions::rotate()` does
the opposite: it marks the existing row `revoked_at = NOW(), revocation_reason =
'rotated'` and **INSERTs a new row with a fresh `Uuid::new_v4()`**. There is no
identifier that survives a rotation today.

Taken as-is, `sid = auth_sessions.id` would change on every refresh, so a Class B
elevation would die at the next token refresh rather than after 10 minutes, and
a Class C challenge issued before a rotation would fail verification after it.

Two ways out, and this is a design fork:

* **A. Split the concepts.** `auth_sessions` becomes a *session* (stable id,
  created at login, revoked at logout) with a child *refresh-token generation*
  that rotates within it. `sid` is the session id. Costs a migration and a
  rewrite of `create`/`rotate`, and makes logout-all a single-row operation
  rather than a sweep.
* **B. Rotate in place.** Keep one row per session and `UPDATE` the
  `refresh_token_hash`/`refresh_jti` on rotation instead of inserting. Smaller
  change, but it discards the per-generation audit trail that the current
  insert-and-revoke pattern produces, and the concurrent-rotation regression
  test in AUTH-002 depends on the losing rotation seeing an already-revoked row.

**A is recommended.** B trades away evidence that AUTH-002 currently relies on.

There is also an ordering consequence: `issue_access_token(wallet, role, mfa)`
takes no session, and `auth_jwt.rs` issues both tokens *before* calling
`auth_sessions::create`. Embedding `sid` requires minting the session identifier
first and passing it into issuance.

### 2. Decision 4's resource-version binding has no substrate — needs a definition

None of the Class C target tables carries a version, revision or `updated_at`
column. `patient_access_requests`, for example, has only `id`, `requested_at`
and `status`. "Target resource version when applicable" is therefore applicable
almost everywhere and available almost nowhere.

Adding a version column to every Class C table is one answer, but two cheaper
ones fit the 120-second challenge window:

* **State-machine resources** (access requests, consent, guardian records) have
  a natural concurrency token already: the terminal-status field. Binding the
  challenge to `status = 'pending'` and re-checking it inside the mutation
  transaction gives exactly the TOCTOU property Decision 4 asks for, with no
  schema change.
* **Row-level resources** can bind to PostgreSQL's `xmin` system column, which
  changes on every update and needs no migration. `xmin` is not stable across
  `VACUUM FREEZE` or a dump/restore, which rules it out for long-lived tokens —
  but a 120-second challenge is well inside its useful life.

Recommend defining the concurrency token per resource class rather than as one
universal column.

### 3. "Canonical request body" is undefined, and today's implementation is not canonical

Decision 4 requires a "digest of the canonical request body" and Decision 5
verifies it. The existing signature path hashes `JSON.stringify(body)`, whose
output depends on JavaScript property insertion order. Two clients — or one
client after a refactor that reorders a struct literal — produce different
digests for the same logical body, and the failure is intermittent and
maddening.

This needs an explicit canonicalisation rule (key ordering, whitespace, number
formatting, Unicode normalisation) written once and implemented identically on
both sides, or the digest must be taken over the exact byte sequence the client
transmits, with the server hashing the raw body it received rather than a
re-serialisation of the parsed value. The second is simpler and less
error-prone.

### 4. Break-glass under Class C conflicts with the emergency product promise — BLOCKING

Class C includes "break-glass issuance", and Decision 5 forbids any fallback
when stronger authentication fails. MediChain's stated purpose is that a
paramedic taps an NFC card and sees blood type, allergies and contacts within
three seconds, without internet. A wallet prompt in that path is a wallet prompt
at a roadside, on a shared device, possibly offline — and if the authenticator
is unavailable, fail-closed means no emergency access at all.

This is a clinical-safety versus security trade and it belongs to the deciders,
not to the implementer. Realistic options: exempt break-glass *issuance* from
Class C while keeping break-glass *extension* and *revocation* inside it;
compensate with narrow scope, short TTL, mandatory post-hoc review and
notification; or require a different authenticator for emergency responders. The
existing register already flags emergency access and NFC issuance as owner
decisions in `check-write-authorization.py`; this is the same question arriving
from the other direction.

### 5. "Wallet proof" is not one assurance level

Decision 3 treats a wallet signature as uniform, but MediChain has two signing
paths. The Polkadot extension prompts the user, which is evidence of
authentication intent in the NIST sense. Staff who sign in with employee ID and
password unlock an `encrypted_keystore` held client-side
(`staff_credentials.encrypted_keystore`), and a key derived from it can sign
without any further human interaction.

Both produce a valid signature; only one demonstrates that a human approved
*this* action. Decision 7's "avoid blind signing" is about display, but the
deeper issue is that a silent signer satisfies Class C mechanically while
providing proof of possession only.

Recommend that the authenticator type be recorded in the audit event for every
Class B and Class C authorization, so assurance is auditable after the fact, and
that Class C either require an interaction-demanding authenticator or record
explicitly that it did not.

### 6. Challenge issuance needs its own rate budget

Class C challenges are per-transaction. `auth_challenges` currently enforces
five per wallet per minute, which is correct for login and too low for a
clinician signing a run of orders. The step-up and transaction-authorization
challenge endpoints need a separate, larger budget — still bounded, still
enforced across replicas by the same advisory-lock pattern, but not sharing the
login budget.

### 7. Authorization *failures* should be audited, not only successes

The required-validation list tests behaviour but does not require that a failed
Class B or Class C authorization produces an audit event. Failed exact-signing
attempts — wrong subject, replayed challenge, changed resource — are the
clearest available signal of an attack in progress, and they are exactly the
events that leave no other trace. Recommend adding them to Decision 6's audit
requirement.

### 8. Relationship to ADR-0003 should be stated

ADR-0003 records wallet auth with JWT sessions. ADR-0008 changes the token
schema and the role of the wallet signature within an authenticated session. It
should say explicitly whether it amends ADR-0003 in part or supersedes it, so a
later reader does not have to infer which document is current.

### Already satisfied, for the record

* Decision 2's requirement that the server never take identity from the request
  holds today: `Claims.sub` **is** the SS58 wallet address, so resolving the
  wallet from the verified subject needs no credential-registry lookup and no
  `key_id` disambiguation while one wallet per subject remains the model.
* Every user has a wallet, including password-authenticated staff, via
  `staff_credentials.wallet_address` and its encrypted keystore. Decision 2 is
  therefore implementable for all roles, subject to item 5 above.
* The one-time challenge primitives Decision 4 needs already exist in
  `auth_challenges`: durable storage, single-use via `used_at`, TTL, SHA3 nonce
  hashing, and a per-wallet budget serialised across replicas by a PostgreSQL
  advisory lock with a passing six-way concurrency test. The transaction
  challenge should extend that table rather than introduce a parallel one.
* The AUTH-003 work already landed the negative half of Decision 5: a session
  that has ended yields no identity at all rather than falling back to the
  legacy header, and three regression tests fail against the pre-fix source.
