# Uncalled backend endpoints — triage worklist

Generated by `python scripts/unused-endpoints.py` (re-run it; do not hand-edit
the counts). As of 2026-08-18: **399 backend routes, 338 called by a frontend,
61 uncalled.**

An uncalled route is not automatically dead. It is one of four things, and they
need opposite responses. Nothing here should be deleted before it is triaged.

---

## A. Intentionally UI-less — keep, no action

These are called by infrastructure, not by the SPA, so "no frontend caller" is
the correct state.

| Endpoint | Caller |
|---|---|
| `GET /health`, `/health/db`, `/health/ready` | Docker healthchecks, load balancer |
| `GET /api/health/telehealth` | telehealth provider probe |
| `POST /api/notifications/sms/inbound` | Africa's Talking inbound webhook |

## B. False positives — called, but not as a string literal

The scanner matches `'/api/...'` literals. These are reached another way, so
they are *not* unused.

| Endpoint | How it is actually reached |
|---|---|
| `GET /api/events` | `EventSource` in the SSE hook |
| `GET /api/telehealth/join/{session_id}` | deep link / QR target, opened as a URL |

Improving the scanner to follow `EventSource` and `window.open` would remove
these two.

## C. Unfinished features — **the real worklist**

Backend exists and works; no UI was ever built. Each is a feature the product
claims to have. Ordered by how load-bearing the feature is.

### C1. Emergency capsule management (headline feature)
```
POST /api/patients/{patient_id}/emergency-capsule
POST /api/patients/{patient_id}/emergency-capsule/revoke
GET  /api/patients/{patient_id}/emergency-capsule/access-log
POST /api/emergency/nfc-token
POST /api/emergency/grants
GET  /api/emergency/grants/{id}
POST /api/emergency/grants/{id}/revoke
```
The encrypted capsule is the product's core promise. Providers can read it, but
nothing in either portal lets a patient or admin **create, revoke, or audit**
access to it.

### C2. POPIA retention administration (compliance)
```
GET  /api/admin/retention/register | report | holds | restrictions | approvals
POST /api/admin/retention/approvals            | approvals/{token}/decide
POST /api/admin/retention/approvals/{token}/execute
POST /api/admin/retention/holds                | holds/{id}/release
POST /api/admin/retention/restrictions/{id}/lift
GET  /api/admin/cds/audit
```
An entire approval-gated retention workflow with no admin screen. The daily
retention task runs report-only, so nothing surfaces its output.

## Rule

Do not delete from this list. Move an entry to *done* by either building the UI
(section C) or recording the superseding route (section D).
